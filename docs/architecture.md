# v12 架构与执行流程

## 入口与执行

`start.py` 隐藏读取 token，启动编译后的 `dist/src/cli.js`。CLI 读取订单与可选在制状态，校验配置、锁和源码指纹，再启动并行构造、CP 和模型任务。

```text
当前订单 / 设备配置 / 已发生的在制事实
              ↓
         Harness 调度器
         ↙     ↓      ↘
通用快速构造  主模型策略   原始经验 / 经验卡
         ↘     ↓      ↙
  构造算法任务 / CP 补全 / CP 改善
              ↓
   物理审计 + 状态核对 + 完整模型验算
              ↓
 最好合法基线 / HTML / 反馈 / 分阶段 Memory
```

主模型可提交受限 Python 构造算法，控制候选范围、分支、回退和资源日历 API 调用；不能修改受保护的工艺、设备、运输约束与审计器。通用构造和 CP 不等待主模型才开始工作。

## 状态与时间

- `python/production_state.py`：当前生产事实，包括已开始运输、在炉/锻打中的工序、炉温、车辆可用位置和时刻；不把未发生的未来计划伪装成历史。
- `python/calendar_engine.py`：部分排程与资源占用日历；允许向已预约的未来任务之前插入不冲突动作。状态句柄记录在 `state_store.py` 的父状态/动作链中，有限缓存淘汰不删除搜索分支。
- `reference/longda_cpsat/transport.py`：CP 时间、选炉、车辆和资源约束；直接联立求解，不按五分钟步长逐格模拟。内部每分钟三 ticks。
- `src/live_state.ts`：区分生产状态版本与搜索版本。最好成绩提高不等于工厂物理状态改变；任务启动时绑定最新合法基线。

目前未接入 Stroma。现有独立日历和 CP 模型使用统一输入，并以完整校验约束交付。

## 构造、补全和改善

1. 通用构造或模型算法从当前输入重新计算方案，完整候选通过双重校验后可立即发布基线。
2. 可用部分构造可以作为 CP 提示尝试补全。提示可移动，补全成功不表示原部分安排能原样续接；UNKNOWN 不证明无解。
3. 已有完整方案后，CP 按 press_gap、vehicle_link、furnace_batch、day_boundary、broad 等方向释放不同订单范围，要求严格改善当前目标；保温偏好允许同首日分数下的次级改善。
4. 构造失败、代码错误或明显低分进入反馈修正；后续任务保留策略归属。通用 CP 不冒记为模型策略贡献。

补全保留独立准入与额度，具体机制见 `src/search_policy.ts`；历史 v7 接力语义见 [architecture-v7.md](architecture-v7.md)。

## v12 调度变化

- `src/task_pool.ts`：已有任务在跑时也可以在当前可用范围覆盖完后换种子轮次，持续补充通用任务。
- `src/generic_cp_policy.ts`：同一基线、提示、方向/范围、额度和线程配置的任务一次最多一个运行；连续无收益后暂缓，冷却结束恢复探索。随机种子变化不清零失败次数。
- 实际释放订单另建记录。不同请求第一次落到同一实际范围仍可能重复，统计会保留事实。
- 冷却不是工艺剪枝或整场早停；UNKNOWN 不当不可行。已有任务不会因进入冷却被取消。

## Memory、辅助模型与恢复

Memory 分 `construct`、`cp_complete`、`cp_improve` 三阶段保存；卡片声明必须对应同阶段证据。辅助模型 qwen3.7-plus 压缩反馈和提出结构化更新，程序校验后应用。检索、执行、合法与改善分别计数。

检查点保存基线、队列、策略、修正与冷却账本；显式 `--resume` 恢复同版本运行，重新启动未完成任务，不恢复 CP-SAT 内部树。数据与原始证据不随 Git 分发。

## 校验与版本边界

`reference-manifest.json` 冻结 reference 内的 22 个文件，`guard-manifest.json` 冻结 4 个核心状态/审计模块。v12 发布保留服务器上的算法和规则，只补充仓库文档与忽略项。运行记录必须按各自版本和源码指纹解释，旧验收不是新版本性能结论。
