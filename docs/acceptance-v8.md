本版放在 `/home/huanzz/longda-strategy-harness-v8-20261020`。v7 目录及用户原有运行任务未修改或停止。此次测试均设置明确的短时上限，测试结束后没有留下新的长期搜索。

## 实现范围

1. **当前状态**：固定订单/在制输入与变化的搜索状态分开版本化。每次模型请求、工具交互刷新；提交时若基线显著变好，要求模型适配或重新确认。当前基线含工序诊断摘要，不只有分数。
2. **失败与低分反馈**：程序错误、构造死路、额度不足、合法但较差分别处理。低分方案保留，不覆盖好方案；暂停关联的普通 CP，把当前基线、候选、具体错误和诊断交给模型。
3. **计算分配**：部分补全有独立额度账本和并发上限；取消每策略强制 CP 配额、UNKNOWN 自动翻倍额度。无收益及时返回策略反馈；保留少量探索。
4. **证据与模型上下文**：按需读取 API、源代码、原始试验；关键已读源码保持可见，重复读取拦截；记录实际提示来源、算法变化、请求状态版本。最终文字答复未完成时，已有合法工具结果仍保存。
5. **验证**：短时新旧比较、模型关闭/开启区分、真实反馈纠错、回归测试和规则哈希对比。

这些搜索策略属于计算资源偏好，不能当作数学最优性剪枝；低分或 UNKNOWN 不等于无解。

## 真实模型的定向反馈纠错

这是功能验收，**不是上表的性能对照**。两条初始输入都是构造策略/算法代码，重新计算当前 20 单，没有导入完整排程答案。

| 步骤 | 实际结果 |
|---|---|
| 已验证构造策略重新运行 | 获得合法基线 519 分钟 |
| 待修正构造重新运行 | 合法，但只有 340 分钟 |
| 质量反馈 | 明确给出 340 vs 519、差 179 分钟，暂停该策略普通 CP |
| 模型第一次改写 | 改了分组和算法；执行器拒绝间接调用 `wf(...)`，明确记录代码错误 |
| 将原始错误反馈模型第二次修正 | 模型改成直接构造分组，不再间接调用函数 |
| 再执行 | 完成 160/160 道，完整双重校验通过，492 分钟 |
| 基线更新 | 492 仍低于 519，因此保留 519 |

两次短调用累计运行 **150.42 秒**，其中模型调用累计 **128.88 秒**；不含两次命令间的人工间隔。该测试 **CP 改善/补全搜索调用为 0**，仍执行完整模型验算。修正的构造从 340 提到 492，但没有超过已有基线，不把它写成整体排程收益。

这验证了“低分反馈→模型改算法→精确语法错误→再修正→执行与审计→保留较好基线”。同时也说明模型不能保证第一次生成的代码就正确。针对这次错误，API 提示补充了不支持函数别名/间接调用的说明；最终还补齐候选/基线诊断与工具证据读取，回归通过，没有对这些最后的提示和记录补充再做单独速度推断。
