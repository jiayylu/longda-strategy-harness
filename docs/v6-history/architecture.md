# v6 执行边界

订单/在制状态 → 冻结规则 → 通用构造与主模型并行。

主模型 → 读取实际 API/历史经验 → 编写构造代码 → 语法校验/短时执行 → 分类反馈 → 修订或最终提案。

完整候选 → 原物理审计＋完整 CP 模型验算 → 发布基线/HTML → CP 在指定范围寻找改善 → 按实际基线记录收益 → Memory 证据更新。

## 状态与正确性

状态句柄始终指向保留的父状态/动作记录。LRU 仅控制32个实体状态缓存；淘汰后按记录重建。检查点存根状态与动作记录，不依赖对控制器里的整数猜测引用关系。候选缓存16组；动作身份稳定。生成代码只能使用签发的动作；不提供生产规则写接口。

增量检查只跳过未受动作影响且已检查过的资源。差分测试对每个提出动作比较原全量检查的可接受性；最终两套完整校验继续保留。生成时间候选仍有限，不能证明全局无解。

## 结果分类

- COMPLETE/AUDITED：完整候选且完整审计通过才能交付。
- BOUND_PRUNED：当前固定部分不能改善指定目标；不是生产不可行。
- CANDIDATE_DOMAIN_EMPTY：当前生成候选范围为空；不是全空间无解。
- PROGRAM_ERROR：代码语法、API或运行时错误。
- BUDGET_EXHAUSTED / RESOURCE_BUDGET：资源额度结束，保留进度。
- CP INFEASIBLE：仅在固定前缀/局部问题范围内有效。
- UNKNOWN / OUTCOME_UNKNOWN：尚未得出结论，禁止转换成无解。
- TOOL_NOT_STARTED：已确认未执行；与执行结果未知区分。

## 费用与恢复

各模型 API 请求都计数；总墙钟时间从启动计到结束。回合记录只保存可见答复和工具事实，不存思考内容。相同执行回执可复用；不把限时失败永久当作算法失败。改输入、执行额度或显式 rerun 可以重新尝试，进行中的相同请求不会同时重复运行。

模型工具的实际执行进入策略统计及 Memory 事实。重放回执不再次发布、不再次奖励。主模型、辅助模型和搜索可能并行，各环节累计耗时不等于整场墙钟时间。

参考机制与边界延续 docs/reference-adaptation.md；v6 具体采用 DeepSeek 的结果逐步提交、错误反馈、预算分类，Qwen 的请求身份与回执机制。没有复用对方的排程求解器，也没有把请求 LRU 用来删除搜索分支。
